    一、项目目标
    
    第一版目标：
    
    - 管理员可以创建、禁用、重置用户密码
    - 用户通过用户名 + 密码登录
    - 所有登录用户都可以查看所有知识
    - 普通用户可以发布、编辑、删除自己的知识
    - 管理员可以管理所有知识
    - 知识支持多级分类、标签、Markdown 所见即所得编辑、摘要、图片、附件
    - 支持标题、正文、标签的简单模糊搜索
    - 支持按分类、标签、发布时间筛选
    - 支持点赞、收藏、浏览数、一级评论和评论回复
    - 支持站内通知
    - 支持后台管理和基础统计
    - 支持暗色模式
    - 使用 Docker Compose 部署到云服务器
    
    一点五、已确认关键决策

    - 项目名称：knowledge-base
    - Markdown 编辑器：Vditor
    - 登录 token 存储：localStorage
    - JWT 有效期：20 天
    - 用户修改密码或管理员重置密码后，旧 token 立即失效
    - 删除策略：文章、评论、附件均使用软删除；第一版不做恢复页面
    - 草稿可见范围：作者和管理员可见
    - 归档文章：列表默认不显示，但所有登录用户仍可通过详情访问
    - 浏览数：做简单防刷，同一用户同一天同一文章只计一次
    - 评论层级：只支持两层，即评论 + 回复；删除父评论时子回复一起软删除
    - 文件上传：支持临时上传，文章保存后再绑定
    - 图片和附件：统一存入 attachments 表，通过 usageType 区分
    - 附件预览：图片和 PDF 可预览，Office 文件和压缩包第一版只下载
    - 标签去重：Vue 和 vue 视为同一个标签，保存时 trim，并用小写 normalizedName 唯一约束去重
    - 分类删除：有子分类或有文章绑定时禁止删除
    - 标签删除：自动解除文章关联，再软删除标签
    - 发布时间筛选：使用 published_at，排序可支持 published_at / updated_at
    - 首页热门知识：按浏览数排序
    - 通知：支持已读和删除，删除使用软删除
    - 管理员重置密码：管理员手动输入新密码
    - 用户改密：保留用户自己修改密码功能
    - 审计日志：只记录关键操作
    - 详细开发文档：personal/docs/知识库开发文档.md

    二、最终技术选型
    
    前端：
    
    - Vue 3
    - TypeScript
    - Vite
    - Naive UI
    - Pinia
    - Vue Router
    - Axios
    - Markdown 编辑器：Vditor（Markdown + 所见即所得）
    - Markdown 渲染：编辑器自带或 markdown-it
    - XSS 清理：DOMPurify
    
    后端：
    
    - Node.js
    - Express
    - TypeScript
    - Prisma
    - PostgreSQL
    - Zod
    - JWT
    - bcrypt
    - Multer
    - Pino 或 Winston
    - Swagger / OpenAPI
    
    部署：
    
    - Docker
    - Docker Compose
    - Nginx
    - HTTPS
    - PostgreSQL 容器
    - 本地文件存储挂载 volume
    
    我建议后端先用 Express，不用 NestJS。因为你的目标是理解后端流程，Express 的抽象少，更适合入门。

    第一版只记录关键操作，例如创建用户、禁用用户、重置密码、删除文章、删除评论、删除分类、删除标签、置顶文章、管理员修改文章分类或标签。
    
    
    关键约束和索引建议：
    
    - users.username 必须唯一
    - categories.parent_id 要避免循环引用
    - tags.name 建议唯一，避免同一个标签重复出现
    - knowledge_tags 使用 knowledge_id + tag_id 联合唯一
    - knowledge_likes、knowledge_favorites 使用 knowledge_id + user_id 联合唯一，防止重复点赞和重复收藏
    - knowledge_items.status、category_id、author_id、published_at 建索引，方便列表筛选和排序
    - comments.knowledge_id、comments.parent_id 建索引，方便查询评论列表和回复
    - attachments.knowledge_id、attachments.uploader_id 建索引，方便查询文章附件和用户上传记录
    - 删除策略要提前定：文章、评论、附件建议第一版优先软删除，避免误删后无法恢复
    
    学习重点：
    
    - 什么是一对多：用户和文章
    - 什么是多对多：文章和标签
    - 什么是自关联：分类 parent_id、评论 parent_id
    - 什么是冗余字段：view_count
    - 什么是关联表：knowledge_tags
    
    五、权限规则
    
    第一版不要做复杂 RBAC，直接用两个角色：
    
    管理员：
    
    - 创建用户
    - 禁用用户
    - 重置密码
    - 管理分类
    - 管理标签
    - 管理所有文章
    - 管理所有评论
    - 查看统计
    - 设置文章置顶
    - 修改文章分类和标签
    
    普通用户：
    
    - 查看所有已发布知识
    - 创建知识
    - 编辑自己的知识
    - 删除自己的知识
    - 点赞
    - 收藏
    - 评论
    - 回复评论
    - 上传自己文章中的图片和附件
    
    接口权限判断可以这样理解：
    
    text
    是否登录？ -> auth middleware
    是不是管理员？ -> admin middleware
    是不是文章作者？ -> owner check
    
    
    学习重点：
    
    - 登录认证和权限授权不是一回事
    - 认证：你是谁？
    - 授权：你能做什么？
    - 后端必须做权限判断，不能只靠前端隐藏按钮

    阶段 2：用户和登录系统
    
    目标：
    
    - 管理员可以创建用户
    - 用户可以登录
    - 后端可以识别当前用户
    
    任务：
    
    1. 设计 users 表
    2. 创建 Prisma migration
    3. 写 seed 脚本创建初始管理员
    4. 实现密码 hash
    5. 实现登录接口
    6. 实现 JWT 生成
    7. 实现 auth middleware
    8. 实现 /api/auth/me
    9. 每次鉴权时查询用户状态，禁用用户即使 token 未过期也不能继续访问
    10. 明确 token 过期时间，比如 2 小时或 1 天
    11. 前端做登录页
    12. 前端保存 token
    13. 前端加路由守卫
    14. 后台用户列表
    15. 管理员创建用户
    16. 管理员禁用用户
    17. 管理员重置密码
    
    JWT 简化方案：
    
    - 第一版使用 20 天有效期的 access token，不做 refresh token
    - token 放在 Authorization: Bearer 头里
    - logout 第一版只做前端清除 token，不承诺服务端立即让 token 失效
    - 如果后续需要真正的服务端登出，可以增加 token 黑名单、refresh token 轮换，或者改成 HttpOnly Cookie session
    - 后端 auth middleware 每次都要检查用户是否存在、是否被禁用、密码重置后是否需要重新登录
    
    验收标准：
    
    - 管理员账号可以登录
    - 登录后能获取当前用户
    - 未登录不能访问内部接口
    - 禁用账号不能登录
    - 禁用账号已有 token 也不能继续访问接口
    - 管理员可以创建和禁用用户
    
    你会学到：
    
    - 密码为什么不能明文存
    - bcrypt 是什么
    - JWT 是什么
    - middleware 是什么
    - 后端如何保护接口
    - 前端如何处理登录态

    - 单文件限制 100MB
    - 文件存储在服务器本地
    
    任务：
    
    1. 设计 attachments 表
    2. 配置 Multer
    3. 设置上传目录
    4. 限制文件大小 100MB
    5. 限制允许的文件类型
    6. 实现图片上传接口
    7. 实现附件上传接口
    8. 实现附件下载接口
    9. 实现附件预览接口
    10. 下载和预览接口都要做登录鉴权
    11. 上传文件使用服务端生成的安全文件名，不直接使用用户原始文件名作为存储路径
    12. 校验文件扩展名、MIME 类型和实际文件特征，不能只相信前端传参
    13. 限制单用户或全站上传总容量，避免磁盘被打满

    附件预览建议：
    
    - 图片：直接预览
    - PDF：浏览器 iframe 预览
    - Word/Excel：第一版可以先下载，不强行在线预览
    - 压缩包：只下载
    
    这里要注意，你说“可以预览附件”，但 Word、Excel 的在线预览会复杂一些。MVP 建议先做到：

    十二、几个重要提醒
    
    1. 附件预览别一开始做太重
    
    图片和 PDF 预览比较简单。Word、Excel、压缩包在线预览会明显复杂，建议第一版先提供下载。
    
    2. Markdown 必须做安全处理
    
    文章和评论都是用户输入，渲染成 HTML 时一定要防 XSS。
    
    前端可以用：
    
    text
    DOMPurify
    
    
    后端也可以对内容做必要限制。
    
    3. 权限必须以后端为准
    
    前端隐藏按钮只是体验优化，真正安全一定在后端判断。
    
    比如：
    
    - 普通用户不能删除别人的文章
    - 普通用户不能访问 /api/admin
    - 禁用用户不能登录
    - 已登录 token 也要检查用户是否被禁用
    
    4. 文件上传要限制大小和类型
    
    你设定 100MB 很合理，但要注意：
    
    - Nginx 有上传大小限制
    - Express/Multer 有上传大小限制
    - 前端也要提示大小限制
    - 文件名要由服务端重新生成，避免路径穿越、重名覆盖和特殊字符问题
    - 文件类型要做服务端校验，不能只相信前端传来的 MIME 类型
    - 下载和预览接口也要鉴权，不能把 uploads 目录无保护地暴露成公开目录
    - 要限制总容量或至少监控磁盘空间
    - Docker volume 要挂载，否则容器重启文件可能丢
    
    5. JWT 和登出策略要提前想清楚
    
    第一版可以用短有效期 JWT，并在前端 logout 时清除 token。
    
    但要知道：如果不做 token 黑名单或 session，后端无法让一个未过期的 JWT 立刻失效。所以 auth middleware 必须每次检查用户状态，禁用用户、删除用户、密码重置后要有明确处理策略。
    
    6. 备份不是二期功能
    
    只要部署到真实服务器并开始上传文件，就要有最基本的备份。
    
    第一版至少要做到：
    
    - PostgreSQL 可以通过 pg_dump 备份和恢复
    - uploads 目录有定期备份
    - 备份不要只放在容器内部
    - 文档里写清楚恢复步骤
    
    7. 数据库迁移要从一开始就用 Prisma migration
    
    不要手动改数据库表。后端学习里，migration 是很重要的一环。
